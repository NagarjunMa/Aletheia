# ALE-56 generation admission

Every authenticated outreach or YC generation first reserves one rolling 24-hour daily slot. After grounding and any credit reservation, immediately before the model call, the server atomically checks one active generation per user, six starts per ten minutes, and 60 output-budget work units per 24 hours. Work units equal the server-configured maximum output tokens rounded up to 1,000-token units: ordinary outreach and legacy YC cost one; canonical YC batches of one through five questions cost two, four, five, seven, and eight. A YC batch remains one daily request and four credits. These budgets are abuse controls, not billing prices.

Limits can be tuned with `EXTENSION_DAILY_LIMIT` (1–100, default 30), `GENERATION_BURST_LIMIT` (1–100, default 6), and `GENERATION_WORK_UNIT_LIMIT` (8–1000, default 60). Invalid values fall back to defaults. The in-flight lease lasts three minutes to recover from a crashed server. Admission has a 10-second transport deadline and rejects late responses even if cancellation is ignored; the provider has a 30-second abort signal covering headers and body consumption. Both deadlines stay below the recovery lease; model SDK and extension automatic generation retries are disabled so one admission cannot trigger hidden repeat calls. A rejected call returns a code and truthful `Retry-After`; unavailable database admission returns 503 and never calls the model. Upstream provider throttling is 503, not a user-quota 429.

## Rollout and monitoring

Apply the new Supabase migration before deploying the server callers. Deploy the server and extension 1.0.20 to a preview wired to an isolated Supabase project; run `ALE56_TEST_PG_BIN=<local PostgreSQL bin> npm run test:generation-admission-db` and exercise all four generation categories. The 6/60 policy is provisional: confirm normal multi-question usage and provider spend before enabling for production. Do not lower limits below observed legitimate use without an explicit decision.

Use first-party structured logs only. Monitor `repository.generation_attempt_start` denial codes (`GENERATION_IN_PROGRESS`, `SHORT_WINDOW_LIMIT_REACHED`, `WORK_BUDGET_REACHED`) and `ADMISSION_RPC_FAILED` / `ADMISSION_RPC_TIMEOUT`; compare them with generation category, bounded work units, provider token counts, 429/503 response rates, duration, and credit refunds. Investigate repeated five-question attempts, denial spikes, `ADMISSION_FINISH_FAILED` / three-minute lease expiries, and provider spend anomalies. Never log prompts, questions, resumes, profiles, generated drafts, tokens, or raw SQL errors.

The additive migration revokes the obsolete user-only RPC grants, so old server callers fail closed during a rolling deployment. Roll back to a previously verified release that still uses identified reservations; do not restore the unsafe release grants. If no such release exists, disable generation while deploying a forward fix. Revert extension 1.0.20 if its UI needs rollback. Do not drop reservation or admission tables as part of an emergency rollback; preserve them for reconciliation. After any rollback, review daily-slot/refund discrepancies before re-enabling the new policy.
